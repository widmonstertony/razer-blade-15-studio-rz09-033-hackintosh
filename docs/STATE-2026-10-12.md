# My 26.7.1 results — two configurations, not one combined success

[简体中文](STATE-2026-10-12.zh-CN.md)

I use the exact RZ09-0330Q / BIOS 1.06 hardware documented in this repository. These results are for macOS 26.7.1 / 25G241, not the old 26.2 release.

## My successful OLED-wake configuration

I completed one Apple-menu Normal Sleep/Wake on October 12, 2026 (Pacific time), with NVIDIA paused and the original SSDT-DDGPU table enabled. OLED 4.7.2 and the original R4 service were active. The system logged real Normal Sleep followed by wake; R4 logged `NUDGE_V3_PASS` and `WAKE_RESCUE_PASS`. I saw a horizontal strip briefly flash at the top, then Apple Watch unlocked my computer and the desktop returned.

4.7.2 fixes an observed phase-gating gap: on Darwin 25.6, rawclock and DDIA restoration is deferred while sleep is pending until an explicit framebuffer-0 resume boundary. It does not retime the successful R4 sequence. That change alone did **not** resolve my black-screen test while the DDGPU table was disabled. The later successful combination is evidence, not proof of a single root cause or a physically measured GPU power rail.

What I have and have not verified:

- Wi-Fi, speakers/microphone and trackpad: I previously confirmed them after a full cold start. This publication does not change their drivers or root patches.
- OLED: one successful menu-sleep cycle in the NVIDIA-off state. Repeated cycles, physical-lid sleep and long-term stability on 26.7.1 remain pending.
- Lock: Apple Watch unlocked this successful cycle. I have **not** independently qualified a password-only lock on this build with Watch locked.
- 10-bit: I manually restored and verified `30-Bit Color (ARGB2101010)` at 1680×945 HiDPI / 3360×1890 / 60 Hz. R4 had returned the framebuffer to 8-bit; automatic retention is not fixed. I chose not to add another program/service or change R4 for this.
- Headphones, Bluetooth, every application/API, thermal behavior and every power state are not collectively qualified. I do not describe the machine as “perfect.”

This independent backup branch is the **sanitized NVIDIA-off public baseline** with OLED 4.7.2; publishing it does not update `main`. The configuration comes from my verified pre-NVIDIA-return physical backup, replaces identity/passwords with public placeholders and pins the existing probe-disable state with `NVRAM.Add.nullmoth-remove=1` and a matching Delete entry. Its stripped public binary has matching non-debug sections/symbols, but is not the exact private binary from my successful boot. USB-test it on your hardware. My private raw ESP, root-patch transaction, identity, Windows BCD and logs are not uploaded. A GitHub checkout is not a full OS backup.

## My NVIDIA-restored configuration — automatic initialization passed, sleep failed

I asked to restore NVIDIA app access. Before staging it, I backed up the current physical ESP, the three kernel collections, original R4 files, existing NVIDIA startup helper/list/plist and NVRAM. The installer verified the backup and fresh physical readback. It changed only:

1. `SSDT-DDGPU.aml` Enabled: `true → false` in the EFI configuration (the AML itself is unchanged).
2. Removed the temporary `nullmoth-remove=1` variable under Apple's boot GUID.
3. Enabled the already installed `com.tonytan.nvidia-app-only` startup job for the next boot; it was **not** bootstrapped or kickstarted in the current boot.

OLED 4.7.2, R4, Intel display properties, Wi-Fi/audio/HID, security and the active kernel collections are unchanged. No new driver or service was installed, no GPU call was made, and no automatic sleep/reboot occurred. The existing service still uses one guarded initialization per boot and refuses unknown file/build/hardware states.

**This reversed a condition of the successful OLED wake, and NVIDIA-active sleep failed again.** I cold-started and the existing service initialized NVIDIA successfully, reporting 16 GiB. I then manually slept at 19:44:57 and the system reported Normal Sleep wake at 19:46:55. R4 started at 19:47:03 but never completed; the WindowServer watchdog recorded approximately 40 seconds without a check-in. Its sampled Intel driver addresses resolve to `IGAccelEventMachine::eventTimeout` and `IGScheduler5::checkForProgress` using the exact 25G241 KDK. I forced a reboot. This shows a graphics recovery stall, not a proven NVIDIA-code root cause. The flag, DDGPU power policy and initialization state changed together. My earlier small NVIDIA Metal tests do not prove CUDA, all applications, full VRAM performance or sleep compatibility.

My current computer remains in the NVIDIA-enabled research state; uploading this backup does not change it. Further work will first isolate initialized-GPU power handling from userland Metal exposure. No automatic sleep loop, firmware retry, live driver unload or watchdog suppression is provided.

## Reproduce or recover

Start with [the exact-build setup guide](MAIN-26.7.1.md) and [root/reinstall requirements](REINSTALL.md). Supply your own identity and legally obtained omitted files. Copying EFI does not install root patches, R4, BetterDisplay or NVIDIA.

For the successful NVIDIA-off configuration on a machine where NVIDIA is already installed: pause the NVIDIA startup job, set the documented `nullmoth-remove=1` probe-disable flag, enable the original SSDT-DDGPU table, then manually fully shut down/start. Preserve all unrelated EFI/Windows/Ubuntu files and exact security settings. Do not call ACPI methods or unload live drivers to imitate this. Make and verify your own backup before any write; my private one-value installer is machine-pinned and is not a universal public installer.

If the existing optional startup job is installed, pause its next-boot launch with `sudo /bin/launchctl disable system/com.tonytan.nvidia-app-only`. Do not uninstall it or hot-unload the GPU. This branch's EFI sets the probe-disable variable at the next OpenCore boot; validate your private USB copy before writing the internal ESP. Until a full cold start actually applies the disabled configuration, the current boot's initialized GPU is still active. Restoring this backup intentionally disables NVIDIA on every boot; a future NVIDIA research configuration must remove the flag from both EFI Add/Delete and the live variable, and separately review DDGPU and service state.

For optional NVIDIA setup, read [the prerequisite, app-only service and recovery guide](NVIDIA-APP-ONLY.md) completely. Do not install a system-UI restriction from an uncommitted experiment: I deferred that change. Do not enable NVIDIA while keeping a table that powers it down and call the combination validated.

If NVIDIA prevents boot on my private installation, I can use its previously installed OpenCore **Space → NVIDIA OFF - Recovery → Y → macOS**, then restore my verified NVIDIA-off state. This public branch does **not** redistribute `NV-Disable.efi` or include its picker entry; its persistent disable flag is the public backup mechanism. Do not assume that private recovery tool exists on a fresh installation. The internal backup and GitHub alone cannot guarantee recovery after losing all boot access. My old 26.2 branch cannot downgrade 26.7.1 or restore its root patches.
